## What was actually wrong

Not one bug. Four, and none of them fails, logs, or shows up in a code review.

**1. The dashboard dictionary had no entry for most of the product — 763 strings.**

The authenticated app is not translated at the call site. Components hold literal English, and a
DOM boundary (`DashboardLocaleProvider`) swaps it at runtime against a dictionary, matched exactly.
A string with no dictionary entry is not an error. It is just English.

I walked `src/app/(app)` and the shared dashboard components with the TypeScript parser, collected
everything a customer can read — JSX text, `placeholder` / `title` / `aria-label`, and the copy
fields of the option, tab and nav tables — and asked the runtime whether it had an answer. It did
not, for 763 of them:

| Surface | Missing |
|---|---|
| Onboarding (the whole flow) | 100 |
| Billing & usage | 39 |
| Email channel setup | 32 |
| Onboarding server actions | 31 |
| IdeaSoft integration | 30 |
| Employee setup fields | 23 |
| Phone-number flows | ~60 across five files |
| Members, security, audit | ~30 |
| Analytics tables | ~30 |
| …and 100+ other files | the rest |

Everything a *new* workspace opens on was in there: every empty state, every setup card, every
error a server action returns.

**2. Onboarding was excluded from the boundary outright.**

The observer bailed unless the path started with `/dashboard`. Onboarding is `/onboarding`. So the
entire setup flow — the first authenticated screens anyone ever sees, the ones that decide whether
they trust the product enough to pay — rendered in English no matter what they had chosen on the
marketing site. One line.

**3. Auth was English end to end, and signup only *looked* translated.**

`/login`, `/forgot-password`, `/reset-password`, `/verify-email`: literal English, including every
error message — the strings a person only ever reads when something has already gone wrong.

`/signup` was worse in an interesting way. It called `getTranslations()` and had a comment
explaining that it was translated. It was not: auth deliberately sits outside `[locale]` (its URLs
are `/login`, not `/tr/login`, so Supabase's callback URLs keep working), so next-intl has no route
segment to read and quietly answers in the default locale. Its heading said "Create account" over a
form already speaking Turkish.

**4. Five public pages were hardcoded, in the sitemap, and linked from the footer.**

`/docs`, `/support`, `/use-cases`, `/contact`, `/about` — plus `/privacy`, `/terms`, the Instagram
data-deletion status page, and the `metadata` on three routes. `/tr/docs` served a complete,
fully-rendered English page. Not a fallback, not a gap. The same page an English visitor sees.

The landing page itself was fine. These are subpages the V3 rewrite never reached.

## What changed

- **823 dictionary entries** added for Spanish, German and Turkish, written to the glossary the
  existing entries had established (`empleado de IA` / `KI-Mitarbeiter` / `yapay zekâ çalışanı`;
  `cliente potencial` / `Lead` / `potansiyel müşteri`). German "plan" copy normalised to
  `Plan`/`Pläne` to match what was already in the file rather than introducing `Tarif`.
- **The observer now covers `/onboarding`.** Same tree, same dictionary, same skip rules.
- **`src/i18n/authLocale.ts`** — auth server components and actions take the cookie locale
  explicitly, so they stop answering in English.
- **The five public pages plus legal, Instagram and metadata** moved into `src/messages/*.json`.

Three things had to change shape rather than just move:

- `SetPasswordForm` decided whether to offer "resend the code" by **matching the English words
  "session expired"** inside an error string. That stops working the moment the string is
  translated. The action names the case in a `code` field now.
- `validatePasswordChange` is a pure, unit-tested module with no translator. It returns a stable
  `reason` beside the English `error`; the caller translates by reason. Existing assertions
  untouched.
- `AuthShell` became a client component. As a server component its `useTranslations` resolved from
  next-intl's request store, and nothing guarantees the layout filled that store first. On
  `/signup` it had not.

One thing I changed that you did not ask for, and should know about: `loginAction` stopped
forwarding `error.message` from Supabase to the customer. It was English, and it was provider
detail they can do nothing with. The server log still has it in full.

## What stops it happening again

Two tests that walk the source with the TypeScript parser and fail on a new untranslated string:

- `test/dashboard-i18n-coverage.test.ts` — the authenticated tree. Allowlist limited to four
  kinds: copy in files nothing renders, form-field names and example data, operator-only strings,
  and words identical in all four languages.
- `test/public-i18n-coverage.test.ts` — public + auth. Every user-visible literal must exist in
  `en.json`.

CLAUDE.md landmine #22 now records the two-systems fact and the six rules that follow from it.

## Two things for you to decide (not engineering decisions)

### 1. `/docs` and `/support` promise things that do not exist

Filed as **R-159**. Translated faithfully, as agreed — but they now say this in four languages
instead of one:

**`/docs`**
- "Automatically create tickets in **Zendesk or Intercom**"
- "Book, reschedule, and confirm appointments through **Google Calendar or Calendly**"
- "sync structured data to **Salesforce, HubSpot**, or custom CRM"
- "**Scale plans include full API access.** Starter and Growth plans use the web interface"
- "**Scale plans support custom model configurations.** Contact sales"
- a whole webhook section telling customers to verify HMAC signatures on endpoints they cannot
  configure

The only commerce integration that exists is IdeaSoft, and it has never run against a real store.

**`/support`**
- "**Contractual SLA** · Guaranteed response times and escalation paths defined in contract"
- "**Community support** and email responses typically within 1–2 business days"
- "Status page coming soon"

There is no community, no contract tier, no status page.

**`/use-cases` and `/about`** are softer but still sell the pre-V3 product — "deploy AI agents on an
architecture designed for multi-tenant SaaS products" — rather than the AI-employee positioning the
landing page now leads with.

Rewrite around what ships today, or unlink and remove. Say which and I will do it.

### 2. Dead code with live-looking copy

About 30 marketing components from the pre-V3 landing are still in the tree, imported by nothing
(`hero.tsx`, `ComparePlans.tsx`, `Security.tsx`, `ProductPreview.tsx`, `TalkToAgentHero.tsx`, the
whole `visual/` folder…), plus four dashboard cards (`WorkloadCard`, `LiveFeedCard`,
`GoLiveReadinessCard`, `AgentPerformanceTable`, `DailyTraffic`). They carry ~250 English strings
that both coverage tests have to explicitly ignore.

They cost nothing at runtime. They cost every future sweep an allowlist. Worth a delete when you
have a quiet moment.
